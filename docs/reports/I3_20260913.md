## §3 禁网守卫（任务 3）

实现于 `bt_fingerprint.py` 的 `install_offline_guard()`：

- 拦 `urllib.request.urlopen` / `urllib.request.urlretrieve`（monkeypatch 抛 `I3OfflineGuardError` 并计数）
- 拦 `requests.Session.request`（requests 内部最终走 `urllib3`，补一层防御）
- 每次拦截记录 `urlopen_attempts` 与调用栈摘要；**禁止静默降级**——回测进程只要尝试外发即抛异常
- 守卫对**本地 sqlite 只读连接零影响**（`sqlite3` 不走 urllib/requests）

### guard-test 输出（离线自检）

```
✓ urlopen 被拦: I3 禁网守卫: 回测进程禁止外发请求 urlopen(http://127.0.0.1:1/x) —— 回测必须离线可复现
✓ urlretrieve 被拦
✓ 本地只读 sqlite 不受影响（MAX(date)=2026-09-11）
守卫计数=2
```

**重要连带发现（engine.py:295，进建议单，本单不动码）**：守卫在真实回测中拦下 6 次 `urlopen`——来自 `engine.py:295` `quotes = df.fetch_quotes(self.codes)`（回测里联网取 `float_mktcap` 做撮合分档滑点），失败后 engine 自身 try/except **静默降级** `kl[-1].amount*20`。守卫把这条"回测悄悄联网、失败悄悄降级"的不可复现根源**显性化**（见 §9 建议单）。守卫拦截后恒走降级分支 → 回测结果与网络状态解耦，可复现成立。

## §4 数据指纹（含内容聚合）

`data_fingerprint(db)` 结构：

```
db / max_date / day_rows / distinct_codes / cov_codes / ratio
+ sum_close / sum_volume / sum_amount        ← 内容聚合（新增）
+ fp_ver = 2                                  ← 指纹定义版本
+ hash = sha256(上述全部，sort_keys)
```

设计要点：

1. **内容聚合**：`SUM(close/volume/amount)` 全表聚合（SQLite 表序固定 → 求和确定性；量级 ~9e7 double 安全）。**没有它，改一行 close 指纹不变，verify 归因失效**——首版 bug 已在开发中实测发现并修复（见 §5 演进注记）。
2. **指纹定义版本 `fp_ver`**：指纹字段集合变化时（如加 SUM）版本 +1，verify 对跨版本记录报"指纹定义版本不同"而非误报"数据漂移"。
3. **参数指纹排除 `tag`**：`tag` 是运行备注（如 `I3验证#1` / `verify:...`），不是回测参数；首版把它混入 params_hash 导致 verify 同参误报"参数不同"，已修复。
4. `--db` 显式传入时切换 `C.DB_FILE`/`C.MIN5_DB_FILE`（finally 恢复），保证指纹与 engine 实际读库一致；`BT_DEFAULT_DB=""` 空 = 锚定生产库。

## §11 风险与回滚

- **回滚**：I3 全部为新增文件/新增配置块，无覆盖既有文件；`app/config.py` 仅末尾追加 I3 块。回滚 = 删除 `tools/bt_fingerprint.py` + 删除 config I3 块 + （可选）清 `data/bt_runs.jsonl`。I1/I2 备份：`tmp/i2/app_{scoring,trader,engine,config}.py_20260913_211541.bak`（SHA256 已校验一致）。
- **风险 1**：守卫若被误装入实盘路径会拦掉实盘 HTTP（`install_offline_guard` 只在 `run`/`verify` 子命令入口调用，且 `engine.Backtest` 是唯一回测载体；实盘 `server.py`/`trader.py` 不经过 bt_fingerprint）——已通过代码路径隔离，无实盘影响。
- **风险 2**：全表 `SUM` 聚合在每次 run/verify 执行（生产库 ~900 万行，实测 1~2s），对分钟级回测可忽略；超大库场景可降级为抽样窗口（见 §9 建议 2）。
- **风险 3**：verify 依赖 `bt_runs.jsonl` 原记录完整（含 codes/参数）；文件被截断/手改会导致 verify 报"记录缺失"——护栏对"数据被手改"的响应是失败而非静默，符合设计。

## §12 与 I1/I2 的衔接

- I1 的 `BACKTEST_OFFLINE`（config）与 I3 守卫是两层：I1 管 earnings 取数路径不联网，I3 管整个回测进程物理禁网——双层兜底。
