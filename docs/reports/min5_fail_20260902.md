## §1 根因判定（证据链，三路独立印证）

### §1.1 核心结论

**2026-09-02 的 min5 日更没有失败——数据完整写入。`data_update_failed` 是"重复触发 + 只看 min5 的达标判定"造成的红字虚惊（狼来了）。**

```
8528 主循环 11:29 卡死 ──► 收盘触发从 15:10 延迟到 15:31:28
                                  │
                    15:31:28 双触发（×2，双 _loop/双进程）
                                  │
                    start_background_update ×2 ──► run_update 防重入仅进程内（updater.py L590）
                                  │
              ┌───────────────────┴────────────────────┐
              ▼                                          ▼
      第一遍（15:34:07）                         第二遍（15:34:09）
      min5 u=1003/1006（成功写库）              min5 u=0（第一遍已写，全跳过）
              │                                          │
              ▼                                          ▼
      数据完整（min5.db 实测 09-02 全量）      L625 达标判定只看 min5：
                                              u=0 < max(1,1006×0.5) → 记 data_update_failed（误报）
```

### §1.2 证据 A：审计链（`data/audit/audit.jsonl` 尾部，行 3537-3539）

```
3537  2026-09-02 15:34:07 data_update         min5_updated=1003 min5_total=1006 min5_rows=48416 min5_errors=0 daily_updated=300
3538  2026-09-02 15:34:09 data_update         min5_updated=0    min5_total=1006 min5_empty=3    daily_updated=300
3539  2026-09-02 15:34:09 data_update_failed  min5_updated=0    min5_total=1006
```
- **先成功后失败**，间隔 2 秒，daily 两遍均 300/0 成功。第二遍 `min5_empty=3`（仅 3 只空，非全池空）→ 与 8/21/24/28 的真失败（`empty=496/1004` 全池空 + daily 300 全错）**本质不同**。

### §1.3 证据 B：min5.db 数据完整性（本块实测，只读）

| 检查项 | 结果 |
|---|---|
| `kline_min5` 09-02 条形图 | 48 根 bar（09:35–11:25 共 23 + 13:00–15:00 共 25）× **1003 码全满** = **48,144 行** |
| MAX(date) | `2026-09-02 15:00:00`（含收盘 bar） |
| 近期逐日 | 08-31/09-01/09-02 均满 bar（1003 码） |

→ **09-02 当日 min5 一档不缺**。审计 `min5_rows=48416` 与实测 48,144 的差异为"新增行数"统计口径（含近期个别码回补），不影响结论。

### §1.4 证据 C：代码路径（`app/updater.py` 原文引用）

- **数据源**：`_fetch_tx_min5`（L64）→ `_tdx.fetch_kline_fast(bare,"min5",...)`；模块 docstring 标注"腾讯 mkline 接口拉 320 根 5 分钟K"（L7）。**超时**：mootdx 15s socket 超时（非无限 hang，half_dead_loop §8 已证）。**重试**：min5 路径**无重试**（L74/L80 每码 try/except 计 errors 后吞掉；对比日线 L359-361、L499-501 有退避重试）。
- **防重入**：L590 `if _UPDATE_STATE["running"]: return {"skipped": True}`——`_UPDATE_STATE` 是**进程内模块级变量**，检查-设置非原子；**跨进程完全失效**。双实例/双引擎各自完整跑一遍。
- **达标判定**：L622-625 `ok = updated >= max(1, int(total*0.5))`——**只看 min5_updated**。第二遍 u=0 → 必判 failed（L632 WARN "保留旧更新日，下次重试"）。
- **写语义**：L238-243 `INSERT OR REPLACE INTO kline_min5` **只增不删、幂等**；`_min5_last_date` 判定 date≤last → `new_rows` 空 → `updated=0` 静默跳过。**第二遍不会覆盖/清空第一遍数据**。

### §1.5 因果归属（谁是因谁是果）

| 现象 | 因 | 果 |
|---|---|---|
| 触发延迟（15:31:28 vs 正常 15:10） | **8528 主循环 11:29-15:31 停摆**（half_dead_loop §7，_loop 线程卡死） | 收盘更新晚 21 分钟 |
| 双触发（15:31:28 ×2） | 多 `_loop`/多进程各触发一次（`_last_data_upd` 为 L309 `_loop` 局部变量，去重失效） | 两次 `start_background_update` |

| 上游故障窗（TDX/腾讯时段性不可达） | **非 09-02 本次失败的原因**——15:34 第一遍 1003 只成功拉取写库，上游当时可达 | 仅关联夜间循环 l2 超时（另一问题，half_dead_loop §7 已判异源） |

## §2 修复方案（只建议，零落地）

### F1｜触发去重：`_last_data_upd` 提升为进程级/文件持久化标记（推荐）
- **做法**：`trader.py` L309/L329-330 的 `_last_data_upd`（_loop 局部变量）改为写 `data/update_state.json` 或模块级变量，多 _loop/多进程共享；触发前先读标记。
- **利**：从源头根治"多 _loop 各触发一次"；改动小（一处变量 + 一处读写）。
- **弊**：进程间读写的原子性需处理（文件写需加锁/原子 rename）；若与 F2 一起做可简化为只依赖 F2。

### F2｜run_update 跨进程防重入：OS 文件锁 + 检查-设置原子化
- **做法**：`updater.py` L590 前加 `msvcrt.locking`（Windows）/`fcntl.flock` 文件锁 + `threading.Lock` 包住检查-设置。
- **利**：补上 L590 的进程内竞态 + 跨进程双重漏洞；与 F1 配合彻底消灭双跑。
- **弊**：文件锁需处理异常/超时/残留锁文件（stale lock 风险）；Windows/macOS 分支实现。

### F3｜failed 降噪：区分"真失败"与"重复空跑"（推荐，见效最快）
- **做法**：`updater.py` L625-639 增加判定——`min5_updated==0 且 min5_empty 小（<10%）且 daily 成功且 last_day==target` → 记 INFO 级 `skip_duplicate` 而非 `data_update_failed`。
- **利**：根治监控"狼来了"（8/19、8/20、8/23、8/26、9/1、9/2 六天都受此污染）；语义上区分 `empty≈total`（真失败）与 `empty 极小`（重复触发）。
- **弊**：只降噪不治本（双跑仍发生，限流压力仍在）；阈值需标定。

### F4｜达标判定引入 daily 信号
- **做法**：`updater.py` L622-625 在 min5 u=0 但 daily 成功时，用"每日一档数据完整性"兜底，不判失败。
- **利**：与 F3 互补；彻底解决"第二遍必报错"。
- **弊**：可能掩盖真正 min5 全缺但 daily 成功的半边残缺（如某日上游只给日线不给分钟）——需保留 empty 阈值。

### F5（本块新增建议）｜引擎停滞检测 + 触发兜底
- **做法**：watchdog 已有"半死"判定（half_dead_loop 报告），建议对 **12:00-15:00 交易时段 heartbeat/事件静默 > 30min** 单独告警，并在 15:45 补一个**独立计划任务**（schtasks）调 `start_background_update` 兜底，不依赖引擎活体。
- **利**：直接治"8528 停摆 → 收盘更新延迟/漏触发"这个更深层因；即使主循环卡死也保证 15:45 前完成 min5 日更。
- **弊**：新增计划任务需协调 Z1/Z2 的调度域；兜底任务本身也可能与引擎内触发器双跑（需配合 F1/F2 的去重）。

> 推荐组合：**F3（立即降噪）→ F1+F2（根治双跑）→ F5（治停摆导致的延迟）**。F4 可并入 F3 一并实现。涉及 `trader.py`/`updater.py`/调度域，落地需人类批准与 Z2 协调。

## §3 诚实披露

**已证实**：
1. 09-02 min5 **数据完整**（min5.db 48 bar × 1003 码全在，MAX=15:00）；`data_update_failed` 为误报。
2. 双触发（15:31:28 ×2）+ 双跑（15:34:07/09）+ L625 只看 min5 的达标判定 = 误报机制链，代码原文引用自证。
3. 触发延迟（15:31 vs 15:10）与 8528 主循环 11:29-15:31 停摆相关（half_dead_loop §7）。
4. 快照/`market.db` 的 `kline(period='min5')` 固定 89,748 行不前进——min5 只写独立库 min5.db，快照不复制（本块新证，属架构性残缺）。

**未定**：
1. **8528 主循环 11:29 停摆的精确卡点不可观测**（无 stdout 重定向，P0 盲区；half_dead_loop §7 原样保留）。

3. 审计 `min5_rows=48416` 与实测 48,144 的统计口径差异未逐码归因（不影响结论）。
4. min5 各历史日是否有细粒度缺口（如 08-31 11:30/13:00 部分 bar、09-01 11:30 仅 1 码）——本块只查了 09-02 全量，未做全史缺口普查。
