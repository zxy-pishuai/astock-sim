### 🔴 P1 缺陷（必然误报，且恰好摧毁本块自身的价值）

`_lp_check_stall` 的判据是 `now - self._lp_phase_since > 300`（`trader.py:390`）。
但 `_loop` 的**非交易分支**（`trader.py:567-594`）只做 `time.sleep(30); continue`，**全程不调用 `_lp_enter/_lp_finish`**；
`finally` 里的 `_lp_flush()` 也**不更新** `_lp_phase_since`。

→ 结论：**引擎 `running=True` 而处于非交易时段时（即每个交易日约 15:05 之后一直到次日 9:10，约 18 小时），`_lp_phase_since` 冻结在最后一次 `_lp_finish`（`monitor`@15:00 附近）**：
1. 约 **15:10** 首次触发 `loop_stall` WARN——**这个时刻与真实收盘链高峰完全重叠**，等于在最需要区分真假停摆的窗口里先放一颗假雷；
2. 之后**每小时一条**，直到次日开盘才可能清零；`loop_stall_cleared` 因 `_lp_stall_start` 永不复位而大概率不发；
3. 并落一份 `stall_trace_*.txt`，栈内容是 idle 循环的 `time.sleep`，无任何诊断价值。

**为什么 9/9 单测抓不到**：五组用例全部是"手动把 `_lp_phase_since` 设成 now-400 再调 `_lp_check_stall`"，**没有任何一条驱动真实 `_loop`**。测试从结构上不可能发现该缺陷。

## §8 追加裁定：废除"后端零第三方依赖"宪法（用户 2026-09-06 批准）

**先纠正本报告 §2 的归因**：内存问题不止 numpy 一处。本班活体取证发现常驻服务里还住着两套额外的东西：

   未带 `main.py:156` 已实现的 `--no-window` → `main.py:132/143` 走 `import webview` + `webview.start()`。
   实测后果：**PID 35108 → 7464 → 5 个 `msedgewebview2.exe`，合计工作集 187.5MB**，
   且服务进程内加载 `clr.dll / clrjit.dll / ClrLoader.dll / WebView2Loader.dll`（pythonnet + WebView2），共 **190 个模块**。
   窗口 `MainWindowTitle` 为空 = **一个没人看得见、也关不掉的浏览器运行时，24 小时挂在交易服务上**。
2. **`main.py:143` 的 `webview.start()` 是阻塞调用，窗口关闭即 `srv.log("窗口已关闭，退出服务")`（`main.py:144`）**
   → 服务寿命当前挂在一个 GUI 消息循环上。属结构性脆弱，非活跃故障。

**运行链第三方全量清点**（静态扫描 + `Get-Process -Module` 双重取证）：
