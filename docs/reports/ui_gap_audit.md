# Y5｜UI/交互差距审计：对标社区成熟量化终端（纯审计·零实现）

> 状态：**完成**。本报告是"界面体验差距"从感觉→清单的产物：现状测绘（实测取证）→ 差距矩阵（×参照系打分）→ 可执行化提案（四要素卡）→ 商用视角。
> **零实现**：web/、app/、server.py 未改一行，无新建前端文件；只读 HTTP（GET）；出网 4/15 次（自证见 §7）。

## §1 现状测绘（实测取证，非臆测）

### 1.1 技术架构
- **形态**：vanilla JS 单页应用（SPA），无框架、无构建链、无路由库。`web/`：index.html 47KB + js/app.js 117KB + js/charts.js 15KB + js/experiments.js 12KB + vendor/echarts.min.js 1MB（本地）。
- **单机免部署**：`python main.py` 起服务即用，浏览器打开 `http://127.0.0.1:8899/`。这是**特性**（本报告所有提案都不得破坏此特性）。
- **页面**（11 页 + 设置）：行情中心 / 实盘交易 / K线分析 / 模拟持仓 / 策略回测 / 因子研究 / 板块资金流 / 盘前新闻 / 全球市场 / 审计复盘 / 实验台账 + 设置。
- **后端 API**：`app/server.py` 共 57 个 GET + 13 个 POST（trade/reset/watchlist/alerts/notify/llm/commission/audit_daily/review/trading_start/stop/scan/twothirty/backtest）。

### 1.2 实测性能基线（curl 只读 GET，2026-09-01 11:00）
| API | HTTP | 大小 | 耗时 | 备注 |
|---|---|---|---|---|
| `/` | 200 | 42KB | 0.06s | 首页 |
| `/api/overview` | 200 | 1.6KB | 0.42s | 行情聚合 |

### 1.3 交互机制取证（app.js 源码）
- **实时性 = 纯轮询**：`setInterval` 9+ 个定时器——trading 3s、portfolio 8s、overview 8s、sflow 5s、market 30s、pnews 60s、brief 30s。**WebSocket / EventSource / SSE 计数 = 0**。
- **错误处理**：HTTP 封装 `fetchJson()`（app.js L38）有 `if (!r.ok) throw`；全文件 44 处 try/catch，但**分布不均**：
  - ✅ AI 报告（晨报/体检/会议/问诊）、回测启动/进度 有完整错误提示（"XX失败: …"）；
  - ❌ **高频轮询函数多数无 try/catch**：`refreshTrading`(L120)、`refreshPortfolio`(L899)、`refreshSectorFlow`(L2018) 直接 await → 数据源异常时 **unhandled rejection，用户无感知**；
  - ⚠ `refreshMarket`(L448) `catch (e) { /* 静默 */ }` → 吞错，页面数据"僵住"无提示。
- **缓存**：`klineCache` 内存缓存（K线页）、localStorage 少量（盘前简报去重）。
- **响应式**：viewport meta + `@media (max-width:1100/900px)` 有；**无暗色模式**（`prefers-color-scheme` 计数 0）。
- **交互深度**：K线页有加载/失败态、缓存；有"加自选"；但**无图表内下单**（交易表单在 trading 页，与 K线/行情页分离，无"图→动作"闭环）、无全局键盘快捷键、无数据刷新时间戳可见化。

## §2 差距矩阵（×参照系，0-3 分：0=缺失 1=弱 2=中等 3=对标/领先）

参照系选择理由：vnpy WebTrader（国内最主流开源实盘终端，实时性范式）、qlib 报告页（学术回测报告叙事标准）、OpenBB/TradingView（当代商用终端交互范式）。出网证据见 §7。

| 维度 | 本系统 | vnpy | qlib | OpenBB/TradingView | 判定 |
|---|---|---|---|---|---|
| 信息架构（导航/页面组织） | 2 | 3（日志/交易/委托/成交/持仓/资金六面板） | 2 | 3（彭博式多面板） | 11 页平铺无分组，中差距 |
| 实时性 | 1（纯轮询 3-60s） | 3（REST+WebSocket 推送） | 1 | 3（实时行情流） | **最大差距**：轮询延迟+无效请求 |
| 交互深度（图→钻取→动作） | 1（无图内下单/无钻取/无键盘） | 2（图表+下单集成） | 1 | 3（Shift+B/S 一键交易、DOM 下单、订单预设） | **大差距**：分析与执行割裂 |
| 错误态/反馈 | 1（轮询静默失败、200+error） | 2 | 1 | 2 | 中差距：死数据无提示 |
| 回测报告叙事 | 1（有回测页，无标准报告面板） | 1 | 3（CAR/回撤/超额/换手/IC 标准图集） | 2 | **大差距**：研究价值未可视化 |
| 可访问性（暗色/移动/键盘） | 1（有响应式、无暗色、无键盘） | 1 | 1 | 3（暗色+快捷键体系） | 中差距 |
| 部署形态（商用演示） | 2（单机免部署，单用户无鉴权） | 2（有登录） | 2 | 3（多形态 SDK/API/面板） | 商用演示需补只读模式 |

**Top 差距（10 项内，按"商用演示价值 × 修复成本"排序）**：① 实时性轮询→SSE；② 轮询错误态统一；③ 回测报告标准面板；④ 暗色模式；⑤ 图→交易闭环；⑥ 11 页信息架构分组；⑦ 键盘快捷键；⑧ 数据刷新时间戳；⑨ HTTP 错误语义；⑩ 移动端单列。

## §3 提案化（每条四要素卡）

> 四要素 = 动哪个文件 / 多大改动面（行数级）/ 依赖哪个后端能力是否已有 / 风险（会不会碰 8899 重启）。
> ⚠ 通用风险提示：任何 `app/server.py` 改动**需重启 8899 服务**，而盘中（09:15-15:00）禁止重启（红线）——全部后端类提案须收盘后部署。

### P1 实时性：轮询 → SSE 推送（最高商用演示价值）
- **文件**：`app/server.py`（新增 `/api/stream` SSE 生成器）+ `web/js/app.js`（EventSource 替换 3-8s 高频轮询）。
- **改动面**：后端 ~80-150 行（行情快照 + 事件循环推送）；前端 ~100-150 行（EventSource 订阅 + 断线重连）。
- **依赖**：后端已有 `overview`/`quotes`/`trading/status` 数据源，SSE 只需"读同一批数据 + 定时推"；**已有**。
- **风险**：⚠ **碰 8899，需收盘后重启**；SSE 连接需服务端线程管理 + 心跳；离线重连逻辑。

### P2 错误态统一（轮询失败可见化）
- **文件**：`web/js/app.js`（统一 wrap 高频轮询函数，失败置顶"⚠ 数据刷新失败 HH:MM:SS"+ 保留旧数据）。
- **改动面**：小，~50 行（一个 `safePoll()` 包装器替换 4 个无 catch 轮询）。
- **依赖**：无后端改动。
- **风险**：**无重启**，纯前端；不改变数据本身，只加反馈层。

### P3 回测报告标准面板（qlib 式叙事）
- **文件**：`web/index.html`（回测页加"报告区"）+ `web/js/app.js`（~150 行渲染四图：累计收益/回撤/超额/换手 + 风险指标卡）。
- **改动面**：中，~200 行。
- **依赖**：后端 `backtest/pool`+`backtest/status` **已有**；**前置**：需先核验回测结果 JSON 是否含净值序列与换手序列（若缺，需后端加导出字段 → 变后端改动）。
- **风险**：无重启（纯前端渲染，前提是数据结构已够）；若需后端补字段则碰 8899。

### P4 暗色模式
- **文件**：`web/css/app.css`（CSS 变量双主题 ~60 行）+ `web/index.html`（切换开关）。
- **改动面**：小，~80 行。
- **依赖**：无后端。
- **风险**：无重启；注意图表（echarts）配色随主题切换。

### P5 图→交易闭环（K线页一键下单）

- **依赖**：`POST /api/trade` **已有**；K线页已有 `state.code` 上下文。
- **风险**：无重启；⚠ 下单是 POST（模拟盘），演示时需谨慎；建议先做"跳转预填"（不动仓）而非"图内直下"。

## §4 "若只做 3 件事"清单

1. **P2 错误态统一**（~50 行纯前端，零重启）——演示时最致命的"数据不动且无提示"立即消除；
2. **P8 数据刷新时间戳**（~30 行）——配合 P2，让终端"活"且可感知，成本几乎为零；
3. **P4 暗色模式**（~80 行）——商用演示第一印象（现代终端观感）成本最低。

> 理由：三者纯前端、无重启风险，可在**任一交易日盘中安全落地**（不碰 8899），以最低成本完成"演示观感 + 稳健性"两个商用第一印象短板。若允许收盘后重启，优先把 **P1 SSE** 提升到第 2 位（真实时性是演示核心卖点，但需后端重启）。

## §5 商用视角（单列节）

呼应存储调研结论——**代码 ~20MB 才是交付物，UI 是壳**。据此：

1. **多用户**：当前单用户 + 全功能（含交易 POST），无鉴权、无角色。商用演示**不应**直接暴露全功能——需"只读演示模式"（禁交易 POST + 禁重置/触发类）。
2. **只读演示模式**：建议做法（零后端改动可选）：前端层加"演示开关"（隐藏交易按钮 + 只读角标）；或后端加 `demo_mode` 配置（属改 config，走提案流程）。演示路径 = 预生成演示数据 + 只读页面，避免现场误触下单。
3. **API token 化**：当前 `127.0.0.1` 无鉴权，适合本机。若对外/局域网演示，需 API token（轻量方案：启动参数带演示 token，前端 header 携带；不做账号体系）。
4. **交付形态**：UI 无需为"商用多用户"重做——vanilla 单文件是可交付、可单机分发、可被 embedding 的资产。商用重点应放在**后端能力（数据管道/回测/因子）+ 只读演示壳**，而非上 React/Vue 全家桶（那会破坏单机免部署特性，且迁移成本高）。

## §6 尊重既有资产声明

- vanilla JS 无构建链是**特性**（单机免部署、零依赖、可分发），全部提案均为**零构建方案**（原生 ES module / 直接改 app.js / CSS 变量），**不引入** React/Vue 构建链。
- 若未来确有大型前端化需求（如多用户 SPA），备选迁移成本对比：htmx（~14KB 渐进增强）/ lit（web component 标准）/ 单文件 ES module——均不引入构建链；完整框架迁移（Vite+React）估计 5-10 人日 + 引入 node 工具链，与单机免部署定位冲突，本报告不建议。
