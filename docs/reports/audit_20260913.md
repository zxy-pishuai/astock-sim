## P0-A 日K覆盖率长期只有 42~48%，兜底重跑零进展（当前最严重）

`stale_first_budget_exceeded` 连续三天 WARN：

库内实测（每只票的最新日K日期分布）：**最新日期=09-11 的只有 2424 只，=09-10 的有 2582 只**
→ 上周五收盘后，**48% 的票日K还停在周四**。

兜底任务确实按新判据跑了（`data/close_update_cron.log`）：
```
覆盖率未达标（ratio=0.2795，阈值=0.9，未追平票=3839），执行收盘兜底更新（幂等） ...
兜底重跑后：ratio=0.2795，未追平票=3839，仍未达标（留待明日/人工收尾）
覆盖率未达标（ratio=0.2969，阈值=0.9，未追平票=3746），执行收盘兜底更新（幂等） ...
兜底重跑后：ratio=0.2969，未追平票=3746，仍未达标（留待明日/人工收尾）
```
→ **重跑前后 ratio 与未追平票数一模一样，兜底重跑产生 0 进展**。

定量矛盾（预算估算参数失真）：`app/config.py:76-78` `STALE_FIRST_BATCH_EST_SEC=90`、`BUDGET_MIN=600`、`BUDGET_MAX=1800`。
1800s 只完成 2250 只 = **0.8s/只**，即每批 250 只实际约 200s，是估算值 90s 的 **2.2 倍**。
按 90s/批 估算，5328 只需 20 批 ≈ 1800s（刚好顶到 MAX）；按实际 200s/批，5328 只需 **约 4270s**。
→ 预算上限被 MAX=1800 截断，每天必然只追平约 45%。

影响：实盘扫描有一半票用**前一天的日K**算均线/涨幅/突破/量比 → 选股池一半是脏的；回测与实盘数据状态不一致。这是目前系统最大的正确性问题。
