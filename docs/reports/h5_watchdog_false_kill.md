## §0 实证证据（tmp/watchdog.log 原文行，逐字引用）

**样本一（开机预热期，孤立 strike）**：

```
2026-09-06 01:35:07  异常 1/3：l1_tcp=ok | l2_overview=TimeoutError:timed out | l3_audit=audit_age_1775s
```

上下文：01:30:02、01:40:02 均为 `健康 OK`——该 strike 前后两轮健康，**单次超时即自愈**。

**样本二（H3b 批量写库后约 4 分钟，孤立 strike）**：

```
2026-09-06 14:50:06  异常 1/3：l1_tcp=ok | l2_overview=TimeoutError:timed out | l3_audit=audit_age_49474s
```

上下文：14:40:06 另有一次同模式 `异常 1/3`，14:45:01/14:55:01 均为 `健康 OK`——两次各为孤立 strike，未累积。

**参照（9/6 01:05 已实证的恢复链路，15.6s）**：

```
2026-09-06 01:05:07  异常 3/3：l1_tcp=down | l2_overview=URLError:<urlopen error [WinError 10061] 由于目标计算机积极拒绝，无法连接。> | l3_audit=audit_age_7480s
2026-09-06 01:05:07  >>> 恢复触发（连续失败≥3）
2026-09-06 01:05:09  端口 8899 关闭（全死），直接重启
2026-09-06 01:05:22  恢复完成：旧PID=24636 新PID=35108（动作=restarted，耗时=15.6s）
2026-09-06 01:05:22  已记录 restart_ts=2026-09-06 01:05:22，进入 180 秒启动豁免
```

**风险模型（由样本外推，非已发生事故）**：三次样本的 l2 超时均出现在 **l1_tcp=ok（端口活）** 时——服务进程活着但 HTTP 探针在忙。当前判定"l1 活 + l2/l3 任一失败"即进入 recover() 的"半死僵尸"分支（L444-459）`kill_pid + taskkill + clear_lock`。若忙持续跨 3 个检查周期（每 5 分钟一次 → 15 分钟），将误杀健康服务；最危险窗口是交易日 15:10-15:45 收盘链（480s 预算 + 快照写盘 + GIL 争抢），且半死分支在写事务中 `taskkill` 可能留下未提交事务/残缺数据。

## §1 问题建模与判别位

| 探针 | 语义 | 可靠性 | 忙时表现 | 死时表现 |
|---|---|---|---|---|
| l1_tcp（5s 连接） | 端口是否监听 | 高（不依赖业务线程） | 仍 ok | down |
| l2_overview（5s HTTP GET） | 业务响应 + time 新鲜度 | 低（受 GIL/写库争抢） | **TimeoutError / time_stale** | URLError（拒连） |
| l3_audit（尾部 t 字段） | 审计链新鲜度 | 中（非交易 7 天放宽） | 可正常 | 断更 |

核心结论：**l1 是"死"的可靠判据；l2/l3 是"活"的可疑判据**。现行把 l2/l3 失败与 l1 失败同等计 strike、同样走 taskkill，是误杀根因。

复用资产（H5 §2 要求回答的边界）：
- **H4 `watchdog_stale`**（trader `_check_watchdog_heartbeat` → audit CRITICAL）：检测"watchdog 计划任务本身断更"，对象是 watchdog 自身心跳文件 `tmp/watchdog_heartbeat.ts`——与"业务服务是否健康"正交，**不可**作为业务侧活体证据，但可作为 watchdog 自身可信度的前提（watchdog 心跳都断了，谈何判定）。
- **K4b `loop_stall`**（`_lp_check_stall` → audit WARN + `tmp/loop_phase.json` 的 `phase_since` 每轮前进）：**业务侧主循环活体证据**。`phase_since` 新鲜（<300s）⇒ 主循环在推进 ⇒ l2 超时只可能是"忙"而非"死"——这是本方案可复用的最强信号。

## §2 三案设计（含状态机、失效模式、取舍）

### P1 探针分级（推荐必做）

**设计**：把 strike 计数拆两条轨：
- **快通道（FATAL）**：`l1_tcp=down` → 计数 `fatal_strikes`，≥3 立即走现有 recover 快路径（L460-461"端口全死直接重启"）。行为与今日完全一致。
- **慢通道（SLOW）**：`l1_tcp=ok` 但 l2/l3 失败 → 计数 `slow_strikes`，需 `WATCHDOG_SLOW_STRIKE`（默认 5）**或** `WATCHDOG_SLOW_WINDOW_S`（默认 1500s=25 分钟）内持续才允许恢复；恢复前**强制二次复核**：重查 l1 + 读 `tmp/loop_phase.json` 的 `phase_since` 新鲜度（复用 K4b 资产）——新鲜 → 判"忙"，本轮只记 CRITICAL 并复位 slow_strikes；冻结 → 判"疑似卡死"，走 recover（kill+重启）。
- 任一轨任一单轮恢复健康 → 该轨计数归零（现状语义保持）。

**状态机（文字版）**：
```
[每 5 分钟检查]
  ├─ l1=down ──► fatal_strikes++; ≥3 ──► recover(快) ──► restart_ts → 180s 豁免
  ├─ l1=ok 且 l2/l3 全 ok ──► 双轨归零，健康 OK
  └─ l1=ok 但 l2/l3 任一失败 ──► slow_strikes++
       ├─ phase_since 新鲜(<300s) ──► 判忙：CRITICAL + slow_strikes 归零
       ├─ slow_strikes ≥ SLOW_STRIKE 或窗口≥1500s ──► recover(慢，同代码路径) → 豁免
       └─ 否则 ──► 只记日志，等待
```

**失效模式**：
1. 真卡死且 l1 仍 ok（端口活但主循环死）：慢通道把恢复从 15 分钟延迟到 25 分钟（或 5 strike）——**延迟可恢复，能力不丢**（反向论证见 §4）。
2. `phase_since` 文件缺失/损坏：视为"无法证明活"→ 按慢通道阈值恢复（保守，不吞真故障）。
3. 慢通道阈值设太高：真卡死延迟过久 → 由 H2 的 `ExecutionTimeLimit=PT2M` + H1b 的 90s TIMEOUT-BAIL 兜底 watchdog 自身，业务侧则靠 P2 标志精确化。

### P2 业务侧否决权（推荐，与 P1 并用）

**设计**：业务侧在关键写事务期间写只读标志文件（如 `data/logs/busy_write.flag`，内容含 `started_ts`）：
- 写标志时机：收盘链 15:10-15:45 全程、批量回补（H3b 类）起止、停摆快照落盘段。
- watchdog 读到标志且 `now - started_ts < WATCHDOG_BUSY_FLAG_MAX_S`（默认 1500s=25 分钟）→ recover 降级为 `skip_busy`：只记 CRITICAL，**不 kill 不重启**。
- 标志超硬上限 → 忽略标志，照常按 P1 慢通道判定（防标志泄漏卡死）。
- 写标志用原子写（tmp+os.replace），业务侧异常静默。

**状态机（P2 叠加在 P1 慢通道之上）**：
```
[慢通道到达恢复判定点]
  ├─ busy_write.flag 存在且未超时 ──► skip_busy：CRITICAL + 本轮不恢复
  └─ 无标志 / 标志超时 ──► 按 P1 慢通道继续（二次复核 → 恢复或判忙）
```

**失效模式**：
1. 进程在写标志**之前**崩溃/卡死 → 无标志 → 走 P1 慢通道恢复（能力保留，仅延迟）。
2. 标志写入失败（磁盘满等）→ 业务侧异常静默，无保护 → 退化到 P1。
3. 标志泄漏（进程死但文件在）→ 25 分钟硬上限兜底后恢复。
4. 业务侧忘了清标志 → 无清除动作设计（只靠超时），不存在"忘清"问题——标志是**写则有效、不写即无效**的语义，避免"清标志"竞态。

### P3 时间窗保护（可选，作过渡/兜底）

**设计**：交易日 15:05-15:50 默认禁止自动重启（仅记 CRITICAL）；**l1_tcp=down 不受此窗限制**（快通道无条件执行）。

**失效模式**：
1. 静态窗口覆盖不了 01:35 开机预热、H3b 14:50 批量回补等窗口外忙场景——**这正是本轮两个实证样本发生的时间点**，故 P3 单独使用覆盖不足。
2. 15:05 前卡死到窗内 → 延迟到 15:50 后才恢复（最坏 45 分钟）。
3. 窗口外真卡死 → 不受保护，照常恢复（无副作用）。

## §3 取舍结论与推荐组合

| 案 | 判别精度 | 实现成本 | 误杀防护 | 真故障延迟 | 覆盖场景 |
|---|---|---|---|---|---|
| P1 | 高（l1 vs l2/l3 分轨 + phase_since 活体证据） | 中 | 强 | 慢通道 +10min | 一切"忙"场景 |
| P2 | 最高（业务侧精确声明） | 中（需业务侧埋点） | 最强（写事务零误杀） | 仅靠硬上限兜底 | 收盘链/批量写库 |
| P3 | 低（静态窗口） | 低 | 中 | 最多 45min | 仅 15:05-15:50 |

**推荐：P1 + P2 组合**（P1 为分级底座，P2 在写事务窗口内提供精确否决）；**P3 仅作 P2 埋点未落地前的过渡开关**（一行 config 可开关，默认关）。

理由：
1. 实证样本（01:35、14:50）恰在**静态窗口外**，P3 单独上防不住这两类；P1 的分级判别与 P2 的写标志都不依赖时间窗口，覆盖所有忙窗口。
2. P2 的"写则有效"标志语义天然免疫"忘清"竞态，且以 25 分钟硬上限兜底泄漏——比 P3 的静态窗口更精确且更安全。
3. P1 复用 K4b 已产出的 `phase_since`（零新增业务埋点成本），把"端口活但主循环在跑"从"疑似死"改判为"忙"，直接消化样本模式。

## §4 反向论证（红线对表）

**红线一：改后"端口活但进程卡死"未证分支仍必须能被恢复** —— 逐案证明：

- **P1**：卡死 = 主循环停摆 ⇒ `phase_since` 冻结（K4b 的 loop_stall 也会独立报警）⇒ 二次复核判"疑似卡死"⇒ 走慢通道 recover（与快通道**同一套** kill→start_service→等 PID→180s 豁免代码，仅触发判定前置）。恢复能力保留，代价是判定延迟（SLOW_WINDOW 默认 25 分钟上限）。**若该票真卡死，最迟 25 分钟后被杀重启**。
- **P2**：卡死前若已写标志 → 硬上限 25 分钟兜底；卡死前未写标志（更常见）→ 无标志，直接走 P1 慢通道恢复。**两种情况都有恢复路径**。唯一需要声明的最坏情形：卡死且写标志发生在卡死瞬间且标志时间戳距现在 <25 分钟 → 延迟最多 25 分钟。
- **P3**：窗内 `l1_tcp=down` 不受限（设计排除）；窗内卡死但端口活 → 最坏延迟到 15:50 后恢复。**仍可恢复**，只是延迟。
- 综上：三案均为"**延后恢复**"而非"**取消恢复**"，且恢复动作代码路径不变。

**红线二：不得削弱 9/6 01:05 已实证的 15.6s 恢复链路** —— 逐条论证：

- 该链路触发条件 = `l1_tcp=down` 连续 3 次（样本 L674-675 可见 l1=down）。三案对 `l1_tcp=down` 均走**快通道/不受窗口限制**，触发条件、恢复函数体、`RECOVER_THRESHOLD=3`、`STARTUP_GRACE=180` 全部不动。
- 慢通道只是**新增**一条轨，不修改现有快路径的任何一行判定；`recover()` 函数体（DEVNULL 启动、等 PID、耗时日志、restart_ts 落盘）原样复用。
- H1b 的 90s TIMEOUT-BAIL 与 H2 的 ExecutionTimeLimit 不受影响（方案不触碰 watchdog 主流程计时）。
- 可观测回归：H1b 的三层夹具可直接复用断言"l1=down → 快路径 → 15.6s 级恢复"不退化（改后验证见 §6）。

## §5 与既有机制的边界（复用/不重复）

| 机制 | 检测对象 | 判定视角 | 与本块关系 |
|---|---|---|---|
| H4 `watchdog_stale` | watchdog 心跳 mtime | watchdog 自身断更 | 正交；作为 watchdog 可信度前提，不可作业务活体证据 |
| K4b `loop_stall` / `phase_since` | 主循环阶段推进 | 业务侧自检 | **直接复用**：P1 二次复核的业务活体证据；loop_stall 独立报警与守护判定互为印证 |
| H5（本块） | l1/l2/l3 探针 + 写标志 | 守护侧外部判定 | 不重复实现 loop_stall，只消费其产物 |

边界声明：`loop_stall` 是"业务自报是否停摆"；H5 是"守护外部决定是否杀"。两者语义互补——`phase_since` 新鲜 ⇒ 守护信任（忙）；冻结 ⇒ 守护二次复核后恢复。
