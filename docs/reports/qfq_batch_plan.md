## 2. 模板适用性核验（只读）—— 四步模板批量边界

已读：`tools/repair_002594.py`、`tools/data_repair_20260825.py`、`tools/repair_qfq.py`。

### 2.1 备份命名（单票 → 多票）

- 现单票模板：`data/backups/kline_day_{CODE}_before_byd_repair_{ts}.json`（payload `{code, rows, rows_data}`）。
- 现两票模板：`kline_day_600262_600426_before_qfq_repair_{ts}.json`（payload `{created_at, reason, codes:{code: rows}}`）。
- **批量边界**：按批次命名 `kline_day_{batch_id}_before_qfq_batch_{ts}.json`，payload 沿用 `codes:{code: rows}`，**每票附 SHA-256**（批后逐票校验、单票级回滚）。禁止散落成几十个单票文件。
- **教训**：08-26 的 515 票批次**无任何备份**（`data/backups/` 无对应文件）→ 无法回滚。批前哈希备份设为 apply 硬前置。

### 2.2 日期范围守卫可否参数化

- 现状：`repair_qfq.repair_one()` **全量重写该票 day 期**（`INSERT OR REPLACE` 全史），内置"2019 起仍有 >21% 跳变就不写库"守卫（`gaps>0 → 不写库`，硬编码 0.21）。
- `repair_002594` apply 前另有：2019 起无 >21% 接缝、最新收盘对齐、接缝消除对照三重校验。
- **批量边界**：
  1. 守卫阈值 0.21 是主板口径；创科实际 high 阈值 2×20%+1%=41%。现守卫对创科更严（21%~41% 也拦）——**保守方向，沿用不放松**。
  2. "精确日期范围写入"不适用于 repair_one 的**全量重写**模式；批量场景继续全量重写 + 守卫，**不引入局部日期补丁**（局部补丁无法统一复权基准）。
  3. 守卫**不可参数化绕过**（任何让 `gaps>0` 也写库的改动违反红线）。
- **关键坑（断点续跑）**：`repair_qfq.run()` 按 progress 文件过滤已处理票；P46 报告已指出"23 只在 Phase20 progress 被标已完成被续跑过滤"。**批量工具必须支持对指定票强制重跑**（--codes / --force）。

### 2.3 与并发服务写库的锁冲突面

- 现模板：apply 前 `wait_quiet()`（mtime 90s 静默窗口，最多等 900s）+ `MTIME_GRACE_SEC=300`；`PRAGMA journal_mode=WAL` + 单事务。
- **批量边界**：每票一个独立事务（repair_one 内 executemany→commit），**单票失败不影响其他票**（回滚粒度=单票）。批次=逐票串行，批前 1 次 wait_quiet，票间复查 mtime（批中库被写→中止后续票）。执行窗口避开 15:10 更新窗、16:30/20:30 任务窗、9/1 11:10-19:10 禁压测。

### 2.4 失败单票回滚粒度

- repair_one 对 `gaps>0` 的票**根本不写库**（守卫前置）→ 失败无写入残留。
- 部分写入失败点（executemany 中途异常）→ `w.rollback()`（工具层外层 catch 记录，不重写 repair_one）。
- 回滚粒度=**单票**：从批前备份 JSON 取该票 rows，`INSERT OR REPLACE` 整票恢复（命令见 §4.4）。**不提供批次整体回滚**。

### 2.5 对模板的三处补强

1. 批前哈希备份（旧批次缺失）。
2. repair_one 外层 catch + 显式 rollback 记录。
3. 批后哨兵复检（read-only，同 high 口径，确认该批票 high 事件归零、全局单调降）。

## 3. 系统性污染成因（实测，决定队列结构）

### 3.1 成因① 2025-08-14 系统性除权(xdxr)缺失集群

- **31 只票**在 2025-08-13→15 出现 >20% 双日跳变（SQL 全库扫描 `MAX(CASE date='2025-08-13')` vs `'2025-08-15'`）。
- 样本：001400 +103.3%（score 活跃未修复）、000880 +102.6%（已修复）、001332 +97.7%（已修复）、001210 +96.6%（已修复）、603093 +61.6%、002768 +61.1%、001359 +34.0%（score 活跃未修复）……
- 细分：**16 只已在 08-26 批次修复**（证明该日 xdxr 在 mootdx 可用，rebuild 可清）、**2 只未修复且 score 活跃（001400/001359）**、约 13 只未修复但低于 high 阈值（科创 41% / 创业板 41% 或主板 <21%，如 688159 +24.7%、301123 +24.3% 等——仍为接缝污染，severity medium/low，不进队列A但应纳入后续全量治理）。
- 结论：001400/001359 的修复**高置信可行**（同集群 16 只已修复成功）。

### 3.2 成因② 2019→2025 系统性数据洞（72 只）

- 判定 SQL（state.queueB_detail）：`date<=2019-01-04 有行 + date>=2025-07-01 有行 + 2020 全年 0 行` → **72 只**，全部为 2020 年仍在交易的老公司（000712/000728/000751/000786/000795/000830/000921/000931/000969/001965/002036/002078/002094/002125/002130/002171/002213/002223/002277/002340…），非停牌。
- 影响：这些票在 2019-01-04 → 2025-07/08 边界产生 +300%~+580% 假跳变，被哨兵记为 longgap high 事件（占 165 个长间隔事件的大头），也污染 return 类特征。
- **修复方式**：repair_one 从 mootdx 原始日K 重建（mootdx 含 2019-2025 完整数据，几乎必然），重建会**自动回填缺失行并消除边界接缝**——但需在 --check 阶段验证 mootdx 原始数据完整性后执行。列为**队列B（独立回填工作流）**。

### 3.3 成因③ 散点式 per-stock xdxr 缺失

- 日期集群：2023-06 中旬（600348/600039/600295/600123，-32%~-38%）、2021-05（605117 四连跳）、2020-06（000983 -24%）、2019-07（300628 -51%）、2019-05（600971 -21%）、2025-07-18/21（7 只）、2026-02~07（603031/603596/600785/603296/002831/001268/603119 等新接缝）。
- 均属 xdxr 缺失导致 qfq 接缝；repair_one rebuild 可清（前提 xdxr 完备）。这些即队列A 主体。

```

  1) 记录 market.db mtime；wait_quiet（90s 静默窗口）→ 未静默整批中止
```
