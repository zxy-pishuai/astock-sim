## 1. P0 缺陷

### P0-1 指数日K 字段错位（全量 1815 行，100%）

**证据**（`data/market.db` kline, period='day'）：

| code | 总行数 | high<=low | amount>0 | 日期范围 |
|---|---|---|---|---|
| sh000001 | 615 | **615 (100%)** | **0** | 2024-02-29 ~ 2026-09-08 |
| sz399001 | 600 | **600 (100%)** | **0** | 2024-02-29 ~ 2026-08-18 |
| sz399006 | 600 | **600 (100%)** | **0** | 2024-02-29 ~ 2026-08-18 |

抽样（2026-09-08 sh000001）：`open=3935.55, high=3946.53, low=3951.32, close=3935.55, volume=32898246400, amount=0`
→ high(3946.53) < low(3951.32)，且 open==close 同时低于 low，物理上不可能。

**根因**：腾讯 `web.ifzq.gtimg.cn/appstock/app/fqkline/get` 返回的数组序是
`[date, open, close, high, low, volume]`（6 元素，**无 amount**），
而两处代码按 `[date, open, high, low, close, volume, amount]` 位置解析：

- `app/index_timing.py:84`（`out.append((_IDX_CODE,"day",e[0],float(e[1]),float(e[2]),float(e[3]),float(e[4]),float(e[5])*100, float(e[6]) if len(e)>6 else 0.0))`）
- `tools/fetch_index_kline.py:37`（同一套位置解析）

因此落库后：`open` 正确、**`high` 存的是收盘价、`low` 存的是最高价、`close` 存的是最低价**、`amount` 恒为 0（`len(e)==6`，e[6] 不存在）。

反推验证：src = (open 3935.55, close 3946.53, high 3951.32, low 3935.55) → high≥max(open,close) ✓、low≤min(open,close) ✓、low==open ✓，完全自洽。

**影响面**：
- `app/engine.py:377` R2 index_ma 择时：`SELECT date, close FROM kline WHERE code='sh000001'` → 实际拿**最低价序列**判断"收盘是否站上自身 20 日线"。low ≤ close 恒成立 → 判定系统性偏严 → halt 更难解除、半仓恢复更晚，长期压制仓位。
- `app/index_timing.py` 三层因子全部基于 sh000001 日K（MA/趋势/振幅）→ 全部错位；振幅类会得到负值或荒谬值。
- 面板/前端展示的指数 K 线与涨跌幅失真。
- 指数 `amount` 恒 0 → 任何"两市成交额/指数成交额"口径失效。

**今日热修未覆盖**：`app/index_timing.py` 今天新增了 `_idx_stale()` 陈旧补拉（修的是"600 行永不触发 len<120 → 指数停在 08-18"），但**没有修字段序**，所以今天补拉写入的 09-08 那根仍然是错的。且补拉只覆盖 sh000001，`sz399001`/`sz399006` 仍停在 2026-08-18（陈旧 3 周）。

**修复要点**：
1. 两处解析改为 `open=e[1], close=e[2], high=e[3], low=e[4], volume=e[5]*100`；amount 该接口不提供 → 显式置 0 并另找成交额来源（或改用新浪 `hq/kline` 带 amount 的接口）。
2. **历史数据可离线精确修复**（无需联网）：对三个指数代码的全部行做三值轮换
   `new_high = old_low; new_low = old_close; new_close = old_high`（open/volume 不动）。
   修完断言：`high >= max(open,close)` 且 `low <= min(open,close)` 且 `high >= low`。
3. `sz399001`/`sz399006` 的补拉纳入同一条陈旧检测（不要只判 sh000001）。
4. 写入前加统一断言（个股/指数通用）：`high>=low`、`high>=max(open,close)`、`low<=min(open,close)`、`volume>=0`、拒绝 `0<volume<100` 与 `0<amount<1000` 的非物理值。

### P0-2 移动止损 peak 被"建仓前的当日最高价"污染（实盘/回测口径不一致）

**证据**：`data/account.json`
- 002011 盾安环境：`entry_price=11.9119, entry_date=2026-09-08, peak=12.54`
- 今日 11:22:45 买入 → **11:22:46（1 秒后）** 审计即出现 `🛑 盾安环境(002011) 触发移动止损条件：现价11.89 自峰12.54回撤超3%（收益-0.2%）`
- 阈值（`app/config.py:51-52`）：`TRAILING_ACTIVATE_PCT=0.04`、`TRAILING_STOP_PCT=-0.03`
  → 12.54 ≥ 11.9119×1.04=12.388（激活成立）、11.89 ≤ 12.54×0.97=12.16（触发成立）。
  但这个 12.54 是**买入之前**早盘冲高的高点，不是持仓期间的峰值。

**根因**：`app/trader.py:1504-1510`
```
peak = pos.get("peak", entry) or entry
if hi > peak and hi <= entry*2.0 and hi >= cp*0.5:   # hi = 当日最高价
    peak = hi
```
`hi` 取的是**当日最高价**，买入后第一次刷新就会把建仓前的涨幅记到持仓头上。
对照回测：`app/engine.py`（建仓时 `peak=price`，随后 `if bar["high"] > pos["peak"]` 只用**建仓之后**的 bar）→ 回测干净、实盘污染，**两者口径不一致**。

### P1-3 情绪门禁 fail-open：数据缺失/异常时默认放行开仓

`app/trader.py:815-817`：
```
if not senti_data:
    self._event("WARN", "情绪数据缺失，按默认可开仓——请检查情绪数据源")
    senti_data = {"open": True, "phase": ""}
```
`app/trader.py:829-830`：`except Exception: pass` → 情绪闸门整块被跳过。

即：**情绪源抖动/冷缓存/任何异常 → 门禁静默失效 → 照常开仓**。这与"冰点禁开仓"的设计意图相反（风控类闸门应 fail-closed）。

本次已核实：今日 11:22:45 的 2 笔买入**不是** fail-open 造成的（审计全天无"情绪数据缺失"WARN；11:21:31 后冰点告警停止，是 `app/limitup.py` 11:24 热修相关的池刷新让情绪真实转好）。但该设计是遗留风险，一旦碰上重启冷缓存就会在冰点日开仓。

**修复要点**：改为 fail-closed（拿不到情绪 → 禁开仓 + CRITICAL 告警），或至少"连续 N 次拿不到才降级为中性且限制单笔仓位"；`except Exception: pass` 必须记录异常到 audit（当前是完全静默）；补一条冷启动用例：进程启动后 60s 内扫描必须走 fail-closed 分支。

```
watchdog 12:05:11：恢复完成 旧PID=38504 新PID=13108（动作=restarted）  ← 但 38504 至今没死
```

代码层面的两个缺陷：
- `main.py:169` `port = srv.find_free_port(args.port)` 在 `main.py:172` `_acquire_lock(args.port)` **之前**执行 → 端口决策基于过期状态。
- `main.py:67-107` `_acquire_lock` 的判据是 `if alive and healthy: return False`（要求 PID 存活**且**端口健康）。当锁里的旧 PID 已死但端口仍健康（或锁文件缺失）时，它会**清锁并写入自己的 PID**，随后在 `main.py:184` `_is_running(args.port)` 分支里"检测到已有实例，直接打开窗口"并 return → **app.lock 从此指向一个纯 UI 进程**。watchdog 后续读锁拿到的属主就是错的。
- `tools/service_watchdog.py:291` `kill_pid` 用 `taskkill /PID x /F` 后**没有校验进程真的消失**，也没有重试 → 今天留下 38504 孤儿。

**幸运的是没有造成重复下单**：38504 在 `main.py:184` 分支就 return 了，交易引擎/后台更新都在该分支之后，未启动；审计确认全天仅 2 笔买入、无重复成交事件。

**修复要点**：`_acquire_lock` 以**端口健康为唯一权威**（healthy → 直接 `return False`，绝不触碰锁文件）；`find_free_port` 移到取锁成功之后；只有"自己确实要 serve"时才写 app.lock；watchdog `kill_pid` 后轮询确认 PID 消失（最多重试 2 次 /F），并把孤儿 PID 写入 audit；启动时若发现自己既不持锁也不监听端口，应主动退出而不是留在内存里。
