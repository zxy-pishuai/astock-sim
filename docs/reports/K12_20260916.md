## 1. 现状核实（关键事实）

- `confirm_no_duplicate`（L733-787）**已有 ★B-G2 半死实例救援**（L770-782）：端口无监听 + main.py 进程龄>180s → `kill_pid`（F5 轮询确认，L490-508）→ `clear_lock` → 放行重启；进程龄≤180s → 拒绝（防新生实例竞态误杀）。
- **缺**：①恢复/拒绝动作只落 `tmp/watchdog.log`，审计流看不到（今日 12:25/12:40 两次拒绝仅有 log）；②lock PID（如 18972）与实际 main.py 进程（如 34096）错配时无显式校验与记录。
- `app/audit.py` 哈希链格式（L400-419）：`rec={t,kind,event,level,**fields}` → `payload=json.dumps(rec,ensure_ascii=False,sort_keys=True)` → `hash=sha256(payload+"|"+prev)[:16]`，跨进程锁 `.write.lock`。
- **audit 事件名注意**：`watchdog_recovered` 已存在于引擎侧（trader.py L374-378，H4 断更恢复语义，触发 `_g3_wd_recovered()` 状态机）。watchdog 侧补写的 `watchdog_recovered` 走同一 record 入口，**语义一致**（看护恢复=心跳/服务恢复，理应清引擎侧断更状态）；新增 `watchdog_refused`（audit.py 无状态机，直接落 INFO/WARN/CRITICAL）。

## 3. 判据证据（tools/test_k12_watchdog.py，28/28 PASS，全 mock 不碰真实进程/库）

### ① 僵尸半死救援（端口 down + main.py 进程龄>180s）

## 4. 生效方式

- 改动在**下一次 watchdog 计划任务轮次自动生效**（每 5 分钟跑 `python tools/service_watchdog.py`，新代码即刻被加载）——**无需重启服务、无需重启 watchdog 进程**（watchdog 每次都是新进程）。
- audit 落盘走 `app.audit.record`，哈希链由官方实现维护（跨进程锁 + 轮转），**不会断链**；`watchdog_recovered` 触发 `_g3_wd_recovered()` 清引擎侧断更状态，语义正确。

## 5. 风险与回滚 / 真实验证 SOP

**风险**：`_audit_record` 每次调起一个 python 进程（~0.5s），仅在恢复/拒绝动作时发生（低频）；subprocess 失败已 try/except 吞掉不阻塞。正则解析 `half_dead_killed_pids` 失败 → `pids_killed=[]` 兜底（不改业务流）。

**回滚**：`Copy-Item tmp\k12\service_watchdog.py.bak_20260916 tools\service_watchdog.py`（恢复原文件）。

**真实验证（判据①②③生产构造，需人工/下一轮次）**：
1. 判据①：服务停摆场景（如 kill 8899 进程留下僵尸 main.py）→ 下一轮 watchdog 应在 <60s 内 kill 僵尸 + 清锁 + 重启，audit 出现 `watchdog_recovered`（action=restarted, pids_killed=[...]）。
2. 判据②：手动写 `data/app.lock` 为一个存活非服务 PID（**测试后还原，勿在生产留错配**）→ 下一轮 kill 僵尸后 `lock_mismatch=True` 记录且恢复不阻塞。
3. 判据③：`Select-String -Path data\audit\audit.jsonl -Pattern 'watchdog_recovered|watchdog_refused'` 应见两类事件。
