### 1.3 52 行分歧分析（N3/N4）

N1/N2/N5 完全一致，N3/N4 差 52 行（0.37%）。可能原因（按可能性排序）：

1. **OHLC 来源差异**：本块用**实库**的 low/high 做落带校验；验收方可能用**快照内**的 low/high。若快照 OHLC 与实库因复权基准不同而有差异，校验结果会翻转。实证：001283 等票 avg≈71 远超实库 high≈55，但仍落在 [low×0.75, high×1.33] 内——这是 qfq 恒定比例方言下 avg（真实成交均价）与复权后 high 的比例差恰好被 1.33 容差容纳。若快照用不同复权基准，边界会移动。
2. **容差边界浮点精度**：52 行集中在 avg 接近 `high×1.33` 或 `low×0.75` 的边界，浮点运算顺序差异可能导致 PASS/FAIL 翻转。
3. **"可安全回灌"定义差异**：本块定义为"至少一份快照 PASS"；验收方可能要求"该 (code,date) 的**所有**正候选都 PASS"或"最佳候选 PASS"。若用更严定义，N3 会更小。

## §2 A/V 落带校验器规格（数据完整性 oracle）

### 2.1 判据

```
avg = amount / volume
合法区间 = [low × 0.75, high × 1.33]
```

- **容差依据**：均价（VWAP）理论上应 ∈ [low, high]，留 ±25%~33% 容差是因为：①集合竞价/大宗交易可略出当日高低区间；②四舍五入；③本库 70.8% 票为 qfq 恒定比例方言，price 是复权后值而 amount/volume 是真实成交，avg/high = 1/复权比例，1.33 上限恰好容纳复权比例 ≥0.75 的票（实测绝大多数票复权比例在 0.8~1.2 之间）。
- **volume 单位**：股（非手），实测 `amount/volume ≈ close` 验证。

### 2.2 分档定义

| 分档 | 条件 | 语义 |
|---|---|---|
| **PASS** | `volume > 1e-6 AND low>0 AND high>0 AND amount>0 AND low×0.75 ≤ avg ≤ high×1.33` | 数据完整可信 |
| **FAIL** | `volume > 1e-6 AND low>0 AND high>0 AND (amount=0 OR avg<low×0.75 OR avg>high×1.33)` | 数据损坏（含 amount=0 坏行与 amount 有值但错得离谱） |
| **UNKNOWN** | `volume ≤ 1e-6 OR low≤0 OR high≤0 OR amount IS NULL` | 信息不足不判定（停牌日浮点下溢、字段缺失） |

**关键补规则**：`volume < 1e-6` 归 UNKNOWN 而非 FAIL——实测最近 60 交易日有 7 行停牌日 volume=5.88e-37（浮点下溢垃圾值）、amount=5.88e-39、avg=0.01，若不归 UNKNOWN 会被误判 FAIL。这些行 open=high=low=close 同一价、chg=0%，是典型停牌日。

### 2.3 校验器 SQL（全量夜间自检）

```sql
-- 本任务不执行，仅规格
SELECT
  CASE
    WHEN volume <= 1e-6 OR low <= 0 OR high <= 0 OR amount IS NULL THEN 'UNKNOWN'
    WHEN amount = 0 OR amount/volume < low*0.75 OR amount/volume > high*1.33 THEN 'FAIL'
    ELSE 'PASS'
  END AS band_status,
  COUNT(*) AS n
FROM kline
WHERE period = 'day' AND date >= ?
GROUP BY band_status;
```

### 2.4 接入点建议

1. **夜间自检事件**：与 `daily_coverage` 同级，每日收盘更新后全量跑，FAIL 行数与占比落 `audit.jsonl`（event=`data_integrity_av_band`），FAIL 率 >0.5% 触发告警。
2. **写侧守卫**：`app/datafeed.py`（L478/507/654）、`app/updater.py`（L98 硬编码 `"amount": 0.0`）、`app/index_timing.py`（L77）落库前对每行做 A/V 校验，FAIL 行拒绝写入并记 audit WARN（指数除外——指数本就无成交额概念，允许 amount=0）。
3. **已知病灶引用**（任务书 §3 已实证，不必重查）：`datafeed.py:478/507/654` 字段缺失默认 0、`updater.py:98` 通达信硬编码 0、`index_timing.py:77` 腾讯指数源缺列写 0。

## §4 回灌方案书

### 4.1 仲裁规则（逐票·日，三条同时成立才回灌）

1. **实库行 FAIL**：含 amount=0（A/V 校验 FAIL）；
2. **候选值 PASS**：至少一份快照的 amount 通过 A/V 落带校验；
3. **≥2 份独立快照给出同一值**：浮点相对容差 0.1%（`|a-b|/max(|a|,|b|) ≤ 1e-3`）。

**收紧后最终可回灌条数：8,003 行**（≤ 验收方 N3=8,160，≤ 本块 N3=8,212）。

损耗解释（8,212 → 8,003，损耗 209 行）：
- 126 行：只有一份快照 PASS（无第二份同值佐证），主要是 08-26 不完整快照单源（83 行）与 09-02/09-04 单源（86+87 行中的部分）；
- 83 行：多份快照有 PASS 但值不一致（快照间 amount 不同，无法确定真值）。

这 209 行归入"不可恢复"路线（R-b 改 NULL 或 R-a 外部重取）。

### 4.2 不可恢复部分（约 6,133 行 / 约 60 只票）的两条路线

| 路线 | 适用 | 代价 | 风险 |
|---|---|---|---|
| **R-a 外部重取** | 约 60 只票（无候选或候选不可信但仍可外部获取） | ~60 次请求（腾讯/新浪带真实成交额）；须逐票重取全史 | **二次破坏风险**：班8 已证 `_fetch_and_save(days=5)` 是"5 天历史重写器"，任何重取路径必须自带"不得把非 0 改写成 0 / 不得写回出带值"守卫 + 写后 A/V 复核，否则会把好数据也弄坏 |
| **R-b 改 NULL** | 全部不可恢复行（含 R-a 失败的） | 语义干净；NumPy 原生 NULL→NaN；与已批准的 S1 读取侧守卫（`tactics.py` amount_ratio 对 NaN 置 None）天然契合 | 下游消费 amount 的代码需有 NaN 防护（实测 `engine.py` L747 有 `or open_px*volume` 兜底、`fflow.py` L131 有兜底；`tactics.py` 已有 NaN 防护） |

**推荐：R-b 为主，R-a 仅对高价值票（常入池 top50）选择性执行。** R-a 执行前必须先实现写侧守卫（§2.4），否则禁止重取。

### 4.3 审计链冲突评估（必答）

- **现状**：本库有哈希审计链（`data/audit/`），全量 `verify_chain()` 因 2026-08-16 断点长期为 False，但**按日口径全绿**（8/16 后每日链块完整）。
- **回灌影响**：回灌是改历史数据，会让被改日（2026 年内 amount=0 的日期）的链块哈希永久失效——因为链块哈希包含 kline 行内容，amount 从 0 改为真值后哈希变化。
- **处理方案（三策，不重签）**：
  1. **影子表留痕**：新建 `kline_amount_recover`（code, date, old_amount, new_amount, source_snapshots, band_check, arbitrage_group, recover_ts），**不原地 UPDATE**，回灌值存影子表，读取侧 COALESCE 优先影子表——这样原 kline 行不变，审计链不受影响。
  2. **豁免登记**：若必须原地 UPDATE（性能考虑），在 `audit.jsonl` 登记 `event=kline_amount_recover`，含被改日清单、旧值哈希、新值哈希、审批人；`verify_chain()` 对这些日期标记"已豁免（amount 回灌）"而非"失败"。
  3. **只读旁证**：影子表 + 快照 manifest 的 SHA256 作为真值旁证，不修改审计链本身。
- **为什么可接受**：回灌是**修复已知坏数据**（amount=0 物理不可能），不是篡改；审计链的目的是防未授权修改，而回灌是经用户批准的修复，留痕后可追溯。重签链块=篡改审计语义（把"修复"伪装成"原始数据"），不可取。

### 4.4 回滚设计

- **影子表先行**：`kline_amount_recover` 记旧值/新值/来源快照/校验结果，禁止原地 UPDATE 无留痕。
- **只回滚本次回灌的精确 SQL 形态**（本任务只写不跑）：
  ```sql
  -- 本任务不执行
  -- 方案A（影子表）：直接 DELETE 影子表中本次批次的行
  DELETE FROM kline_amount_recover WHERE recover_ts >= ? AND recover_ts < ?;
  -- 方案B（原地 UPDATE）：用影子表的 old_amount 恢复
  UPDATE kline k
  SET amount = r.old_amount
  FROM kline_amount_recover r
  WHERE k.code = r.code AND k.date = r.date AND k.period = 'day'
    AND r.recover_ts >= ? AND r.recover_ts < ?;
  ```
- 回滚后必须重跑 A/V 校验确认恢复到回灌前状态（FAIL 行数应回到回灌前）。

## §7 遗留与建议

1. **执行回灌需用户另行点头**：本块只交方案书 + dry-run 证据，不执行任何写库。
2. **写侧守卫优先于回灌**：建议先落地 §2.4 的写侧 A/V 守卫（防新坏行继续产生），再执行回灌（修存量）。否则回灌后日更仍会写新的 amount=0。

5. **审计链按日口径**：回灌日期集中在 2026 年，建议豁免登记按日粒度，不影响 8/16 断点后的按日全绿结论。
