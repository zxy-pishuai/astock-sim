## 3. 三问三答

### Q1：44104 死于什么？

**死因 = watchdog 半死恢复（主动终止），诱因 = 引擎 overview 接口持续超时 + audit 停写。**

- watchdog 12:50 起记录 overview `TimeoutError:timed out`（l1_tcp 仍 ok，进程活着但接口卡死）
- 13:00 连续 3 次失败 → `半僵死 PID=44104（overview=TimeoutError audit=audit_stale_5366s）→ 终止后重启` → 新 PID=52336
- **关键**：这不是"自然死亡/断电"，而是 watchdog 判定"进程活着但服务僵死"后的主动 taskkill
- 之后 9/1 19:05 系统重启才是 52336 的终结者（Id 1074 用户手动重启）

**半僵死根因（需 Y2 深查）**：9/1 13:00 起，每个实例启动后短暂写 audit 心跳，随后 overview 接口即超时、audit 停写 → 15 分钟后被 watchdog 判死重启。39 次循环说明这是**引擎级可复现问题**（overview 接口为何持续超时/线程卡死），不是单次偶发。建议 Y2 排查 `/api/overview` 的 time 字段刷新链路与主线程阻塞点。

### Q2：17940 是谁？

**17940 = 9/2 09:15:40 系统重启后由启动文件夹自启的 main.py 实例，是 09:30 四笔卖出的执行者。**

出生方式（证据链）：
1. 9/2 08:26:04 意外关机（Id 6008）→ 09:15:40 系统重启（Id 41，非正常关机后）
2. 用户登录 → 启动文件夹 `StockService_Recovery.lnk`（mtime 9/1 00:03）→ `tmp/g0_autostart.ps1`（登录延迟 60s → 探测 8899 → Start-Process main.py）
3. audit 09:16:45 恢复写 → 17940 于 09:16 出生（g0_autostart 60s 延迟后 ≈09:16:40）
4. watchdog.log 无"新PID=17940"恢复行 → **17940 非 watchdog 拉起**，与启动文件夹路径一致

### Q3：锁是怎么消失的？（精确成因链）

**根因 = main.py `_acquire_lock` 缺陷 + watchdog 全死恢复不清锁的组合。**

机制拆解（读源码确认）：
1. `main.py` L104-109：锁文件存在但旧 PID 僵死 → `os.remove(_LOCK_FILE)` → `return True, "清理僵死实例"` → **跳过 L110-111 的写新 PID**。即"删了旧锁却不写新锁"。
2. `tools/service_watchdog.py` recover()：半死分支 L298 会 `clear_lock()`；**全死分支 L300 不清锁**（旧锁残留）。
3. 8/31-9/2 期间系统多次重启/意外关机/半僵死循环，锁反复走"删了不写"路径。

本次链条：
```
9/2 08:26  系统意外关机（锁=2112 残留磁盘）
09:15      系统重启 → 09:16 启动文件夹拉起 17940
           → main.py _acquire_lock 读锁=2112（僵死）→ 删锁 → return（不写新锁）
           → app.lock 消失 → 17940 以"无锁"路径启动 → 写锁 17940  ✓（10:10 read_lock_pid=17940 佐证）
09:54:57   17940 死亡（锁=17940 残留）
10:10:08   watchdog 全死恢复（不清锁）→ 8528 启动
           → _acquire_lock 读锁=17940（僵死）→ 删锁 → return（不写新锁）
           → app.lock 消失 → 8528 裸奔运行  ← 当前状态
```
**结论**：只要 main.py 缺陷不修，任何"旧锁残留 + 旧 PID 僵死"的启动都会让锁消失。修复建议（交 Y2，本次不动代码）：main.py L109 在 `return` 前补写 `str(os.getpid())`；或 watchdog 全死分支也 `clear_lock()` 后让 main.py 走无锁写路径。

## 4. watchdog 断档归因（修正任务书）

任务书称"断档 17h（9/1 17:55-9/2 10:05）"——**不成立**。实测两段真实缺口：

| 缺口 | 时长 | 归因 |
|---|---|---|
| 9/1 14:20-19:05 | ~4.75h | 无系统睡眠事件佐证；19:05 用户手动重启（Id 1074）——疑夜间闲置计划任务未触发/调度器停滞 |
| 9/2 07:00-08:26 | ~1.4h | **无 Id 42 睡眠事件 → 非睡眠**。Id 41 明示"system stopped responding, crashed, or lost power"→ **系统 07:00 后进入无响应/濒崩溃状态**，watchdog 计划任务随之停滞，08:26 意外关机 |

**核心结论**：9/1 夜-9/2 上午的真正问题不是"watchdog 断档"，而是（a）引擎半僵死循环（9/1 19:20-9/2 07:00 39 次重启，overview 持续超时）；（b）系统级无响应导致 08:26 意外关机。watchdog 本身工作正常，甚至过于积极（每 15 分钟杀一次半死实例）。**半僵死循环是比锁缺失更紧迫的引擎级隐患**。
