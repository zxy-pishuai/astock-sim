## §2 P0-A（新发现）：watchdog 恢复分支死锁 → 每次恢复后自废

实测链条（不依赖被验方叙述）：

1. `tools/service_watchdog.py` 进程 **PID 25296**（12:15:01 生）到 12:56 仍未退出（>41 分钟）。
2. `tmp/watchdog.log` 冻结于 12:15:08（71949 字节），末行"端口 8899 关闭（全死），直接重启"；`tmp/watchdog_heartbeat.ts` 冻结 12:15:06。
3. 计划任务 `Status=Running`、`Last Run Time` 仍推进（12:40:01/12:45:00），但因 `<MultipleInstancesPolicy>IgnoreNew`，**12:15 之后每轮激活被静默吞掉**（进程表无新 pythonw）。
4. `h1_watchdog_state.json`：`consecutive_failures=4`、`restart_ts=""`。4=旧值 3 加 1；那个 3 正是 9/3 11:35:06"异常 3/3"→11:35:14"半死僵尸 PID=38200，终止后重启"留下的，而**该轮之后再无"恢复完成"日志**。

判读：两次恢复（9/3 11:35、9/5 12:15）同型卡死在 `start_service()` 内、`log("恢复完成")` 之前。该区间唯一无界等待是
`subprocess.run([... powershell ... Start-Process ...], capture_output=True, timeout=30)`：超时后 Python 先杀 powershell（现场已无其子进程），随后第二次 `communicate()` **不带超时**，而被拉起的 `main.py`（pythonw 22272）继承了被捕获管道写端 → 读端永不 EOF → 永久阻塞。

后果三连：① watchdog 从此不再运行，服务裸奔；② `restart_ts` 不落盘 → **STARTUP_GRACE 180s 豁免永不生效**，下次重启后 l2 超时可能再度连环误杀（9/2"51 杀"事故的引信仍在）；③ 恢复结果无日志，旧/新 PID 无从对账。

说明：E2（9/3）修的是固定文件名被僵尸握持**文件句柄**，本次是**管道捕获死锁**，不同源——E2 判据内测试全过，不追溯扣分。
