## 3. QUOTE_CACHE_SECONDS 3s→1.5s 评估

**结论：建议不改**（保持 3s，F 道不改既有常量）。依据：

| 维度 | 分析 |
|------|------|
| 打板路径真实 TTL 影响 | 打板每 5s 轮询（rounds×sleep 5s）> 3s TTL → **每轮取数本就全过期**，TTL 3 与 1.5 对打板首轮无差别 |
| "3s 旧行情"真实场景 | 仅当其他调用方（watch 2s 轮询/展示）刚写缓存、打板轮询在同一 TTL 窗内命中——数据新鲜度 = 最近取数时刻，最坏 3s 旧 |
| 关键路径解耦 | F3 强制刷新已覆盖"接近涨停"候选（≤50 只/轮）——**决策用最新价，与 TTL 解耦** |
| 降 TTL 的收益 | watch 持仓路径（2s 轮询）在 TTL 1.5 下请求全过期——持仓行情更新频率从"2s 一次取数"变"1.5s"——边际收益小 |
| 降 TTL 的风险 | 所有调用方请求频率上限提高（展示/扫描/watch）→ 请求量翻倍，撞 **P62 数据源按 IP 限流**（16 并发已慢）风险大 |
| 后续选项 | 若未来确需更短 TTL，只对 watch 持仓路径设独立常量（F 道后续项），不动全局 |

## 5. 端到端延迟基线（改动前理论测算）

| 环节 | 耗时（常态） |
|------|------|
| 首轮 300 只取数（TDX 快路径 ~55ms/100 只 + enrich） | 0.2~0.5s |
| 候选精评（≤8 只并行拉日K 250 根） | <1s |
| 判定（打分/情绪/风控） | <0.1s |
| **轮询周期（rounds 10×sleep 5s）** | **5s + 各轮耗时 ≈ 5.5~7s** |
| 最坏情况（旧路径，缓存 3s 旧 + 取数 0.5s + 精评 1s） | ~10s（F1/F3 修复前） |

改动后：候选判定用强制刷新最新价，延迟 = 取数 0.2~0.5s + 精评 <1s ≈ **1~1.5s**（不含轮询周期等待）。

## 6. 打板轮询节奏检查（任务 4）

**代码级**（权威）：
- 主循环（trader.py L758/781）：`rounds = 10`，每轮 `_board_round → _exits_round → _watch_round → _price_alert_round` 后 `time.sleep(5)` → **理论轮询间隔 = 5s + 各 round 耗时**。
- **发现**：L781 `time.sleep(5)` 是**硬编码**，未引用 `BOARD_SCAN_INTERVAL` 常量（该常量只在 auction 时段 L700 生效）——若日后调常量，主循环节奏不变（**一致性小缺陷**，报告建议后续将 L781 改为 `time.sleep(C.BOARD_SCAN_INTERVAL)`）。
- `_maybe_launch_scan_async`（L971）：`SCAN_ASYNC_INTERVAL=45` 节流 → **全市场扫描频率 ≈45s/次，与打板轮询（5s）是两个不同节奏**（扫描不阻塞打板，F1/F2 已保证）。
- **单点实测**：`tmp/loop_phase.json` 当前 `loop_seq=93`、monitor 阶段耗时 243ms → 各轮正常量级 <0.5s → 理论轮询 ≈5.5s。
- **历史反推受限**：`data/audit/audit.jsonl` 已轮转（当前 57 行），无历史 board 事件时间戳序列；09-11 停摆（stall_trace_20260911_101443.txt）为极端反例（board 被 fetch_quotes 卡 2142s，F1 已修）。
- **结论**：常态节奏 ≈5.5~7s（p95≤7s 大概率达标），**判据 3 待 F1/F3 上线后交易日实采确认**（audit 轮转后新事件可查）。
