## §2 冒烟网首跑抓到的真问题（★需派单）

### ★R1 指数 amount 被无额源整段覆盖（S05 失败）

```
sh000001 按年：2018~2023 行 1264 · amount<=0 = 0     ← A5 回填的成果还在
             2024 行 242 · amount<=0 = 186
             2025 行 243 · amount<=0 = 243
             2026 行 171 · amount<=0 = 171           ← 全丢
```
- **600 行归零 = 2024-02-29 起的全部行**——正是腾讯 fqkline 单次返回约 600 根的窗口。
- **推断**：A5 的指数 amount 回填成果，被**指数刷新路径用"结构上无 amount 的源"整段覆盖**
  （与 09-09 amount 事故同源：回填只管历史，没堵住增量写入侧）。
- **证据补充**：我 09-13 验收 A5 时实测 `amount>0 = 1918/1918`（100%），今日 1320/1920
  → **确为这三日内发生的回归**。
- **建议修法**：指数写入路径加与个股同款的 UPSERT 保护
  （`amount = CASE WHEN excluded.amount>0 THEN excluded.amount ELSE kline.amount END`），
  或改用带成交额的指数源；并把 S05 作为回归护栏常驻。

### ★R2 生产停摆 21 分钟 + watchdog 被自身守卫卡死（今日 12:20~12:41）

```
12:13:51  main.py 重启（PID 21996）
12:15:02  l1_tcp=ok 但 /api/overview HTTP 500
12:20:06  l1_tcp=down（HTTP 线程已死，8899 无监听）
12:25:06  连续失败 3 次 → 触发恢复 → "端口 8899 关闭（全死），直接重启"
12:25:11  G2 三重确认未过，拒绝启动新实例：main_py_running_pids=[21996]（需人工介入）
12:30/12:35/12:40  继续失败，G2 持续拒绝
12:41     验收方终止 21996 → 启动干净实例 PID 38280 → 8899 恢复
```
- **形态**：进程活着（主循环仍在写 `loop_phase.json`/审计），但 **HTTP 服务线程已死**
  → F5 那轮加的"防双实例"G2 守卫**把半死实例误判为活实例**，导致**自愈能力失效**。
- **建议**：G2 判据加一条——"PID 存活 **且** 8899 可连"才算活实例；只有 PID 活而端口死
  → 判定半死，允许 kill+重启（这正是本次人工作业的逻辑）。
