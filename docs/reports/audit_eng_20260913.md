## P0-J 交易主循环与网页共用同一条行情通道 —— 盘中停摆 35.7 分钟（最严重）

**证据链**
1. audit：`{'t': '2026-09-11 10:14:43', 'kind': 'trading', 'event': 'loop_stall', 'level': 'WARN', 'phase': 'monitor', 'loop_seq': 91, 'streak_s': 1694}`
   → `{'t': '2026-09-11 10:50:26', 'event': 'loop_stall_cleared', 'phase': 'board', 'streak_s': 2142}`
   即 09-11 盘中主循环停摆 **2142 秒 = 35.7 分钟**（约 09:46→10:50）。期间打板轮询（`BOARD_SCAN_INTERVAL=5`）、快速自选监控、止损检查全部冻结。
2. 线程栈快照 `data/logs/stall_trace_20260911_101443.txt`（22,314B，18 个线程）显示**四个消费者同时卡在同一条取数路径**：
   - `Thread-585 (_loop)` → `trader.py:638 _watch_round` → `trader.py:1807 mv.vp_minute_signal` → `datafeed.py:406 fetch_quotes` → `threading.Condition.wait`
   - `Thread-586 (_fast_watch_loop)` → `trader.py:1881 df.fetch_quotes` → `datafeed.py:382` → `tdx.py:176`
   - `Thread-889 / Thread-892 (process_request_thread)` → `server.py:558 _stocklist_paged` → `server.py:290 df.fetch_quotes(全市场)` → `datafeed.py:382`
   - `ThreadPoolExecutor-417_0 / -418_0` → `datafeed.py:374 _fetch_batch` → `datafeed.py:38 _http` → `socket.create_connection`（TCP 连接挂住）
3. 机制：
   - `server._stocklist_paged`（`app/server.py:285-303`）在 30s 内存缓存过期后，对**整个股票列表**调 `df.fetch_quotes`，且 `_LIST_CACHE` 无锁、**无在途去重**。
   - `datafeed.fetch_quotes`（`app/datafeed.py:326-406`）的 `_lock` 只保护缓存读写（:336-342、:399-403），**取数全程不持锁、无 single-flight** → N 个并发调用者各自发起一遍全市场取数。
   - 全市场 ≈5000 只 / `BATCH=400` = 13 批，`ThreadPoolExecutor(max_workers=4)`（:379）**每次调用新建**；腾讯失败后走**串行**新浪回退（:390-398），最坏 13 批 × (10s connect + 10s read) ≈ 260s。
   - 交易路径（`_watch_round` / `_fast_watch_loop` / 打板）与展示路径（`/api/stocklist`）**共用同一个 `fetch_quotes` 和同一个 3s TTL 缓存**（`QUOTE_CACHE_SECONDS=3`，`app/config.py:374`）→ 一次网页刷新即可把交易循环挂死。

**结论**：这不是偶发抖动，是架构性缺陷——实时交易与只读展示没有资源隔离，没有 single-flight，没有全局 deadline。

## P1-L 回测吞吐：`score_stock` 单次 13.4 万函数调用，且 `_signals_on` 全串行

**实测微基准**（1250 根日K，`scoring.score_stock`）
| 指标 | 实测 |
|---|---|
| 冷态首次 | 2413.9 ms（含 DNS+TLS+证书枚举） |

| 热态稳定 | **14.2 ms** |
| 单次函数调用数 | **134,136** |

**放大机制**
- `engine.py:424-469 _signals_on` 对**全部 codes 串行**循环（无线程池；`engine.py:254` 的池只用于 `_load_data`）。

## P1-M 业绩因子在回测里结构性恒为 0（PIT 逻辑对，数据窗口错位）

**实测 PIT 可见性检验**（`earnings.fetch_earnings(60)` 返回 500 条，公告日范围 **2026-07-16 ~ 2026-09-10**）
```
as_of=2019-06-28  可见公告数=   0  bonus=0 signals=[]
as_of=2022-06-30  可见公告数=   0  bonus=0 signals=[]
as_of=2024-06-30  可见公告数=   0  bonus=0 signals=[]
as_of=2026-06-30  可见公告数=   0  bonus=0 signals=[]
as_of=2026-09-11  可见公告数= 500  bonus=0 signals=[]
```
- 根因：`earnings.py:92-145 fetch_earnings` 取的是**相对 `date.today()`** 的近 `days` 天公告（:135-136），`_load`(:75-89) 同样以 today 为基准；而 `earnings_signal`(:148-160) 再用 `notice_date <= as_of` 过滤 → 历史 as_of 恒为空集。
- 后果一：**任何回测中业绩因子恒贡献 0**。库里 `earnings` 表只有 **260 行**，也不足以支撑历史回测。所有"业绩因子有效/无效"的历史结论均不成立。
- 后果二：**实盘 `as_of=None`（今天）→ 因子生效；回测 `as_of=历史日` → 恒不生效**。这是又一处实盘/回测口径分裂（与 P1-N 叠加）。
- 后果三：`earnings.py:57-72 _save` 在**只读回测过程中写 market.db**；`_conn()`(:47-54) 每次调用都执行 `PRAGMA journal_mode=WAL` + `CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS`，且全程持 `_lock`。
- 待确认：`scoring.py:776-777 moneyflow_signals` 调 `ea.earnings_signal(code)` **不传 as_of** → 若被任何回测路径消费即构成未来函数。当前调用方为 `ai.py:86,246`、`consensus.py:65`、`server.py:511`、`trader.py:948`、`updater.py:1179`（均非回测），需固化护栏防回归。

## 优先级与建议执行顺序

| 级别 | 编号 | 一句话 | 预期收益 |
|---|---|---|---|
| P0 | J | 交易/展示取数隔离 + single-flight + 全局 deadline | 消除盘中 35 分钟停摆 |
| P0 | K | 修 audit 轮转误杀 + kill 失败即中止重启 | 消除夜间自伤重启与双实例 |
| P1 | L | 指标 numpy 向量化 + 回测预计算 | 回测 89 分钟 → 分钟级（50~200x） |
| P1 | M | 业绩因子 PIT 数据落地 + 回测禁网 | 修正确性 + 结果可复现 |
